4. THE THINGS THAT WILL GET IT REJECTED — HANDLE THESE BEFORE SUBMITTING FOR REVIEW
--------------------------------------------------------------------------------
(4a) ** TRADEMARK — HIGHEST RISK / very likely rejection **
   The name "PSN Wrapped" stacks TWO trademarks:
     - "PSN" is Sony's mark (PlayStation Network). Using a platform's trademark in
       an app NAME/icon is a common cause of App Store rejection + a Sony C&D.
     - "Wrapped" is strongly associated with Spotify Wrapped.
   STRONGLY recommend renaming to something trademark-free before public launch,
   e.g. "Trophy Rewind", "Platinum Year", "PlayBack", "GG Year". The app's display
   name is `name` in apps/mobile/app.json (and the root app.config.js reuses it).
   The App Store Connect listing name is set separately in App Store Connect.
   ACTION: advise Jonny to pick a cleared name; an IP lawyer review is wise.

(4b) ** NON-FUNCTIONAL PAYWALL — guaranteed rejection if left as-is **
   The app has a Pro paywall (app/paywall.tsx) showing prices (£24.99 lifetime /
   £4.99 seasonal), but there is NO real in-app purchase wired up yet. Apple
   REJECTS apps that display purchasable items without working StoreKit IAP.
   Two options before App Store review:
     (i) Wire real IAP via RevenueCat (react-native-purchases) + create the
         products in App Store Connect, and set ALLOW_DEV_PRO=false on the backend
         (Render env var). The backend already has a pro_status table + entitlement
         endpoints; RevenueCat webhooks would write to it. OR
     (ii) For a first release, REMOVE/hide the paywall pricing and ship the app
         free (no Pro), then add IAP in a later version.
   The dev Pro grant (POST /pro/activate, gated by ALLOW_DEV_PRO) is for TestFlight
   only — it must be OFF for production.

(4c) ** PSN Terms of Service / "uses another service without authorization" **
   The app reads PlayStation data via an UNOFFICIAL API (psn-api) using a session
   token (NPSSO) the user generates. This violates Sony's ToS and Apple reviewers
   may reject under guidelines about using another platform's service without
   permission, or about the token-based login. Mitigations to present:
     - The app is clearly UNOFFICIAL with a visible "not affiliated with Sony"
       disclaimer (already in onboarding/connect/settings).
     - It is read-only and stores no password.
   There is genuine review risk here; be honest with Jonny that it might be
   rejected on this basis regardless of polish.

(4d) ** REVIEWER ACCESS — the app needs a PlayStation account to do anything **
   The core flow requires a PlayStation NPSSO token, which an Apple reviewer can't
   easily obtain. You MUST make review possible:
     - The onboarding shows a DEMO recap (fake data) BEFORE connecting — good, the
       reviewer can see the app's value without connecting. Point this out in the
       "App Review Information > Notes".
     - Provide clear reviewer notes explaining the NPSSO step and that a demo is
       shown first. Consider adding a "Skip / Try a demo" path that doesn't require
       connecting, if not already obvious.
     - The backend is on Render's FREE tier and SLEEPS — the first request takes
       ~50s. A reviewer may think it's broken. Recommend upgrading Render to a paid
       always-on instance (or at least warn in notes), OR add a friendly loading
       state for cold starts.

(4e) ** PRIVACY POLICY URL — required **
   App Store requires a privacy policy URL. There isn't one yet. Need to host a
   privacy policy (the content exists in docs/DATA_HANDLING.md in the repo — it can
   be turned into a public web page). Also fill the App Privacy "nutrition labels"
   accurately (see docs/PUBLISHING.md in the repo for the exact data-type table).

(4f) Account deletion: REQUIRED by Apple and ALREADY BUILT — Settings ->
   "Disconnect & delete everything" wipes tokens + stats (POST /account/disconnect).
   Point this out; no work needed.
